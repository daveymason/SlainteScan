Autonomous Red-Teaming and Terminology Verification Agent for HL7 FHIR R4 APIs

1. Problem Identification and Justification (15%)

Irish hospitals are currently replacing closed HL7 v2 networks with web-facing HL7 FHIR R4 APIs under the Sláintecare reform programme, the Digital for Care 2030 roadmap, and the European Health Data Space (EHDS) regulation. Putting clinical data on REST endpoints makes it much easier to connect patient portals and regional shared care records. Yet it leaves Health Service Executive (HSE) integration engineers and hospital security staff dealing with two stubborn problems at once: silent clinical coding drift and Broken Object Level Authorization (BOLA / CWE-639).

On the clinical side, a FHIR server will happily store a syntactically valid Observation or Condition JSON payload even if the attached SNOMED CT code contradicts the nurse's free-text triage note, or if a LOINC vital sign uses a loose string like mmHg where strict UCUM requires mm[Hg]. On the security side, BOLA sits at the top of the OWASP API Security list (API1:2023) because the HTTP requests that exploit it look completely normal. A user logs in via OAuth 2.0 / SMART-on-FHIR and gets a valid token for Patient/A. If the server verifies the token signature but forgets to check compartment ownership on the requested ID, that user can pull or edit Patient/B's medical history.

Why don't standard testing tools catch this? Static JSON Schema validators only check structure. They cannot read a written note about penicillin anaphylaxis and spot that a coded prescription puts the patient in danger. Traditional Dynamic Application Security Testing (DAST) tools like OWASP ZAP and OpenAPI fuzzers like Schemathesis fail for a different reason. They expect nested URL paths such as /users/123/orders/456. FHIR stores resources in flat endpoints like /Observation/456 and buries patient ownership inside internal JSON pointers (subject.reference) or graph search modifiers like _include, _revinclude, and reverse-chained _has queries. And because a successful BOLA breach returns a clean 200 OK with valid FHIR JSON, single-session fuzzers treat the data leak as a passing test. Kaur (2026) looked at more than 100 real-world BOLA bug bounty reports and found that only 22.6% rely on sequential integer IDs that basic fuzzers can guess; 39.2% use non-sequential UUIDs or hashes, and 41.7% involve state-changing write calls. An LLM agent fits this gap because it can read clinical prose against terminology rules while writing multi-step Python scripts that harvest leaked graph references (like shared Practitioner or Encounter IDs) to test cross-patient access.

2. Data Evaluation (15%)

We cannot touch real patient records for a university project under GDPR and Irish Health Research Regulations. All development and testing in Assignment 2 will run on open standards and synthetic cohorts. For structured patient data, we will generate 1,000 longitudinal FHIR R4 records using MITRE's Synthea simulator, which is freely available under the Apache 2.0 licence (Walonoski et al., 2018). We will add simulated Irish Individual Health Identifiers (IHIs) to those records and load them into a partitioned HAPI FHIR R4 server configured with five SMART-on-FHIR v2 test accounts: two patients (ID_PAT_A and victim baseline ID_PAT_B), a family carer, an acute clinician, and an IoT gateway token. To check clinical codes without relying on the LLM's internal memory, we will pull the public-domain HL7 FHIR R4 StructureDefinition and CompartmentDefinition/Patient JSON schemas (CC0), the LOINC v2.78 table (royalty-free Regenstrief licence), and the SNOMED CT Irish/International RF2 release (free to use in SNOMED Member territories, including Ireland through the HSE).

Unstructured inputs will come from SNOMED CT editorial guides, OWASP API Security test playbooks (CC BY-SA 4.0), and the server's live /metadata (CapabilityStatement) and /.well-known/smart-configuration files. We will also include multimodal data by feeding synthetic scanned triage forms and PDF attachments (stored in FHIR Binary and DocumentReference resources) into an optical character recognition (OCR) step to see if messy handwriting causes coding mistakes or indirect prompt injections. From these sources, our pipeline extracts seven input features: the resource type (resourceType), coding triples (system, code, display), UCUM value blocks (valueQuantity.value and code), graph reference pointers (subject.reference, encounter.reference, Patient.link), OAuth 2.0 scope claims, HTTP status codes with OperationOutcome.issue text, and query latency in milliseconds.

3. Investigate and Compare Current Approaches (20%)

There are a few ways we could apply generative AI to FHIR verification and penetration testing. The simplest option is zero-shot prompting with commercial cloud models like OpenAI's GPT-5.6, Google's Gemini 3.8 Pro, or Anthropic's Claude Sonnet 4.5 (and 5.5). Those models read clinical notes well, but single-turn prompts lose track of state during multi-hop API tests, make up fake 9-digit SNOMED CT codes when ungrounded, and force us to send hospital API schemas to outside servers. A second route is Retrieval-Augmented Generation (RAG) with constrained JSON decoding, similar to static test generators like Karate-BOLA-Guard. Hooking an LLM up to a local SNOMED CT and FHIR schema index stops it from inventing codes. Even so, a plain RAG pipeline is too passive for pen-testing. It cannot run a bash script, inspect a live HTTP 422 Unprocessable Entity error, or adjust a blocked query by itself.

That brings us to autonomous tool-using agents. Recent benchmarks show that how an agent manages its state matters much more than raw model size. In the MAPTA study, letting an LLM call tools without strict guardrails actually correlated negatively with exploit success ($r = -0.31$) because the model wasted its context budget guessing random inputs. Tran et al. (2026) fixed this failure mode in Red-MIRROR by pairing an append-only shared text memory with a Dual-Phase Reflection loop. When a single command fails with a syntax error, local Intra-Reflection rewrites the payload; when an attack vector hits repeated 403 Forbidden blocks, global Inter-Reflection drops that path and switches to a new angle, reaching an 86.0% success rate on the XBOW benchmark (compared to 50.0% for linear PentestAgent runs).

For Assignment 2, we plan to use Qwen3-Coder-32B (alongside the sparse Mixture-of-Experts variant Qwen3.6-35B-A3B for faster local runs, and benchmarked against DeepSeek-V4 and Claude Sonnet 4.5) running locally on Ollama/vLLM inside the OpenHands platform. Under the hood, Qwen3-Coder is an autoregressive Transformer decoder that uses Grouped-Query Attention (GQA) to keep key-value cache memory low, Rotary Position Embeddings (RoPE) across a 128k-token context window, and SwiGLU feed-forward layers (where the 35B-A3B MoE model activates just 3B parameters per token). It is pre-trained on trillions of code and technical tokens before going through Supervised Fine-Tuning (SFT) and Direct Preference Optimization (DPO) on multi-step coding traces. That background makes it very dependable at writing Python HTTP test scripts and picking apart nested FHIR JSON. The obvious trade-off is hardware versus privacy: running a 4-bit quantised 32B/35B model locally takes 18–22 GB of VRAM and generates tokens more slowly than a cloud API, but it costs nothing per token and keeps all hospital telemetry on local hardware.

4. Proposed Solution Design (20%)

For our CA2 implementation, we will package the SlainteFHIR Auditor inside Docker using the OpenHands CodeActAgent harness (Wang et al., 2025). Instead of outputting static text, the agent interacts with the target server by writing and running Python code in a sandboxed container and calling deterministic Model Context Protocol (MCP) tools.

Pointing an LLM straight at 140+ FHIR resource types wastes tokens, so each audit starts with a deterministic Python reachability filter. That script reads /metadata and /.well-known/smart-configuration, compares the server's active endpoints against CompartmentDefinition/Patient, and drops static terminology routes like ValueSet or CodeSystem (trimming the search surface by more than 90%). Once the target map is ready, the OpenHands agent runs two continuous loops. In the Terminology Verifier loop, the agent pulls newly stored FHIR bundles and passes every CodeableConcept and valueQuantity block to our FastMCP server, which queries a local SQLite/Tantivy index of SNOMED CT RF2, LOINC, and UCUM rules. The LLM then compares the free-text clinical notes against the validated codes to catch semantic mismatches or unflagged drug-allergy conflicts.

In the Red-Team loop, the agent first crawls the sandbox using victim token ID_PAT_B to record ground-truth resource hashes and map shared bridge nodes (such as a common Practitioner or Location). It then switches to low-privilege tokens (ID_PAT_A, ID_CARER_A) and writes Python httpx scripts to test six FHIR-specific attack paths: direct leaf reads (/Observation/{id}, /Binary/{id}), forward and reverse inclusions (_include, _revinclude), reverse chaining (_has:Observation:patient:code), dual-membership pivots (performer vs. subject), batch bundle smuggling, and Patient.link compartment annexation. What happens when a query fails? If the server returns 400 Bad Request, Intra-Reflection reads the OperationOutcome error message and repairs the search syntax; if an endpoint returns three consecutive 403 Forbidden responses, Inter-Reflection logs that vector as hardened and moves on. Finally, a Multi-Identity Differential Oracle compares the attacker's response against ID_PAT_B's ground-truth baseline and writes confirmed findings into a SARIF v2.1.0 file (slaintefhir-audit.sarif.json) and an HTMX audit dashboard.

5. Risks, Limitations and Ethics (20%)

Our proposed setup has real technical limits. A local 32B/35B model can still misjudge complex post-coordinated SNOMED CT expressions or lose track of earlier steps during a 25-turn OpenHands session. Summarising large FHIR Bundles into short telemetry tuples to save context space can also hide subtle data leaks tucked inside custom StructureDefinition extensions. And because the agent only tests the HTTP FHIR REST layer, it is completely blind to downstream protocol leaks, such as a hospital server exporting unencrypted HL7 v2 messages to a legacy Mirth Connect interface engine. On the practical side, keeping the full SNOMED CT RF2 database (>360,000 concepts) alongside a 20 GB VRAM GPU and a partitioned HAPI FHIR container takes workstation hardware that small clinics rarely own.

There is also an obvious ethical risk: an automated BOLA and terminology red-teaming agent is a dual-use tool (Barach, 2026). If someone aimed write-level probes (PATCH, DELETE, or Patient.link updates) at a live hospital server, it could corrupt real clinical records or leak patient identities. To comply with GDPR, the EU AI Act, and HIQA audit rules, our CA2 build will hardcode three safety locks into the HTTP client: transport-layer IP pinning that blocks any address outside local RFC 1918 Docker subnets (127.0.0.1/8, 172.16.0.0/12), a mandatory startup check confirming that the target server's /metadata sets CapabilityStatement.experimental == true, and copy-on-write database snapshots so any destructive test resets as soon as the run finishes.
